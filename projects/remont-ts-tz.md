# Техническое задание: CRM-воронка "Ремонт ТС" в облачном Битрикс24

Дата версии: 2026-06-17
Дата актуализации: 2026-07-29

## 1. Цель

Настроить в облачном Битрикс24 отдельную CRM-воронку для услуги организации ремонта поврежденных транспортных средств через партнерские СТОА.

Система должна позволять менеджеру Форсайта:

- создать сделку после согласия клиента на услугу;
- подобрать СТОА и мастера по доступному времени;
- записать клиента на дефектовку;
- поставить задачу мастеру СТОА;
- получить результат дефектовки;
- проконтролировать начало и окончание ремонта;
- организовать проверку качества ремонта;
- проконтролировать оплату комиссии от СТОА.

## 2. Исходный бизнес-процесс

Каналы появления клиента:

- аварийный комиссар на месте ДТП показывает информационное видео и выдает буклет;
- менеджер в офисе при выдаче документов по ДТП предлагает услугу ремонта;
- менеджер обрабатывает входящий звонок, если клиент заинтересовался ремонтом.

После согласия клиента менеджер создает сделку в новой воронке "Ремонт ТС".

## 3. CRM-воронка

Название воронки: "Ремонт ТС".

Рекомендуемые стадии:

1. Сделка создана
2. Запись на дефектовку
3. Дефектовка назначена
4. Результат дефектовки получен
5. Клиент думает
6. Контроль начала ремонта
7. Ремонт в работе
8. Контроль окончания ремонта
9. Проверка качества
10. Расчеты
11. Успешно завершено
12. Отказ / неуспешно

Логика стадий:

- Отдельная стадия "Подбор СТОА" не используется. Подбор СТОА, поиск свободного мастера и создание записи выполняются в рамках стадии "Запись на дефектовку".
- "Клиент думает" используется, если после дефектовки клиент не отказался, но еще не подтвердил ремонт.
- "Отказ / неуспешно" используется для отказа от услуги, неявки без продолжения, отказа после дефектовки и иных неуспешных исходов.
- Результат дефектовки не должен быть отдельным набором стадий. Его лучше хранить в поле "Результат дефектовки" и по значению переводить сделку в нужную стадию.

## 4. Карточка сделки

Полный перечень полей хранится в `projects/remont-ts-reference.md`.

Минимально обязательные поля при создании сделки:

- Контакт
- Источник обращения
- Марка ТС
- Модель ТС
- Госномер
- Описание повреждений

Обязательные данные перед стадией "Дефектовка назначена":

- в поле сделки выбрана СТОА;
- создана связанная онлайн-запись, в которой указаны специалист, дата и время дефектовки.

Отдельные пользовательские поля "Мастер СТОА", "Адрес СТОА" и "Дата и время дефектовки" в сделке не создаются. Специалист, дата и время являются данными онлайн-записи, адрес является данными связанной карточки СТОА. Это исключает ручное дублирование и расхождение данных.

Если при настройке роботов, задач, каскадной рассылки, фильтров или отчетов выяснится, что Битрикс24 не позволяет получить эти данные из онлайн-записи или связанной СТОА, допускается добавить технические поля и заполнять их автоматически.

До запуска необходимо проверить, что дата онлайн-записи может использоваться для срока контрольной задачи, а адрес СТОА, специалист, дата и время подставляются в задачи и сообщения. Отдельно требуется определить обработку переноса и отмены записи, поскольку запуск роботов подтвержден только для создания онлайн-записи.

Обязательные поля после дефектовки:

- Результат дефектовки
- Комментарий мастера

Обязательные поля на стадии "Проверка качества":

- Эксперт Форсайта
- Результат проверки качества

Обязательные поля на стадии "Расчеты":

- Сумма комиссии
- Товар "Комиссия за ремонт"
- Статус оплаты от СТОА

## 5. СТОА и мастера

Нужно вести структурированный список партнерских СТОА.

Реализация:

- создать новый тип CRM-компании "СТОА";
- хранить партнерские СТОА в компаниях CRM;
- создать в сделке отдельное пользовательское поле "СТОА" типа "Привязка к элементам CRM" с выбором компании;
- не использовать стандартное поле сделки "Клиент" для выбора СТОА: в нем остается контакт владельца транспортного средства;
- хранить в карточке СТОА название, адрес, телефоны, график работы, условия комиссии, ответственного и комментарий;
- связать сделку "Ремонт ТС" с выбранной СТОА;
- настроить мастеров как специалистов онлайн-записи;
- для каждого специалиста указывать название компании СТОА как тип ресурса, а имя мастера — как название ресурса;
- при переименовании компании СТОА синхронно переименовывать соответствующий тип ресурсов онлайн-записи.

Пример: для компании СТОА "Кузя" создается тип ресурса "Кузя", внутри которого ресурс имеет название "Илья Иванов". Такая классификация позволяет менеджеру определить СТОА специалиста в расписании онлайн-записи.

Каждый мастер создается как экстранет-пользователь Битрикс24. В профиле мастера обязательны:

- поле "Мобильный телефон";
- пользовательское поле "ID ресурса онлайн-записи" типа "Целое число";
- пользовательское поле "СТОА" с привязкой к CRM-компании;
- активный статус пользователя.

Значение "ID ресурса онлайн-записи" должно быть уникальным среди активных мастеров. CRM-контакт мастера и отдельное поле "Мастер СТОА" в сделке не создаются. Сопоставление выполняется по ID ресурса, а не по ФИО.

Технические поля "ID ресурса онлайн-записи" и "СТОА" заполняются только администратором или интеграцией и не должны быть доступны мастеру для изменения. Если штатными правами портала нельзя запретить редактирование, авторитетное сопоставление `ID ресурса -> ID пользователя` хранится в закрытом хранилище интеграции, а значение в профиле используется только для просмотра и диагностики.

Для подключения нового мастера рекомендуется создавать ресурс через интеграцию и автоматически записывать его ID в профиль экстранет-пользователя. Для пилота администратор может получить ID ресурса через REST API и внести его вручную.

Для сдачи проекта создаются две СТОА и по два специалиста для каждой СТОА. После сдачи пользователи самостоятельно создают новые СТОА, экстранет-пользователей, ресурсы и настраивают их индивидуальные графики по инструкции.

## 6. Запись на дефектовку и календарь мастеров

Требование: у каждого внешнего мастера должен быть свой календарь занятости (функционал онлайн-записи). Менеджер Форсайта проверяет доступные окна и выбирает в сделке свободного мастера и СТОА на время, подходящее клиенту.

Реализовать через "Онлайн-запись" в CRM Битрикс24.

Подтвержденные условия:

- используется облачный Битрикс24, тариф "Профессиональный";
- функция "Онлайн-запись" доступна в текущем портале;
- мастеров СТОА можно завести как ресурсы бронирования или специалистов;
- менеджер Форсайта может вручную создавать онлайн-запись из CRM-сделки;
- запись онлайн-записи можно хранить в карточке сделки;
- штатную автоматизацию можно запускать от создания онлайн-записи;
- интеграция может обрабатывать REST-события создания, изменения и удаления онлайн-записи;
- у каждого мастера должен быть отдельный график приема;
- клиент получает подтверждение записи и напоминание о визите через каскадную рассылку;
- мастер получает уведомление о назначении дефектовки и ссылку на задачу через каскадную рассылку;
- мастер может открыть задачу и оставить комментарий без доступа к лишней CRM.

Каскадная рассылка: Макс -> WhatsApp -> Telegram -> SMS. Рассылка уже настроена в системе. Отдельный резервный канал уведомлений мастера не требуется.

### Интеграция онлайн-записи с мастером

При создании записи обработчик:

1. получает событие `onBookingAdd` и ID онлайн-записи;
2. запрашивает запись и получает `resourceIds`, дату и время;
3. находит единственного активного экстранет-пользователя, у которого поле "ID ресурса онлайн-записи" равно ID выбранного ресурса;
4. получает из профиля ID пользователя, ФИО, мобильный телефон и связанную СТОА;
5. определяет связанную с онлайн-записью сделку;
6. создает задачу непосредственно на экстранет-пользователя;
7. сохраняет соответствие `ID онлайн-записи -> ID задачи`;
8. передает мобильный телефон и ссылку на задачу в каскадную рассылку.

Интеграции нужны REST-разрешения для онлайн-записи, CRM, задач, чтения пользователей и пользовательских полей профиля. Поиск выполняется среди активных пользователей типа `extranet`; обработчик или кэш сопоставления должен подтвердить ровно одно совпадение по ID ресурса.

При `onBookingUpdate` обработчик обновляет срок и текст задачи. Если выбран другой ресурс, задача переназначается новому мастеру, прежний и новый мастера получают соответствующие уведомления. При `onBookingDelete` связанная задача отменяется или закрывается, мастер получает уведомление об отмене.

Обработчик должен быть идемпотентным: повторное событие не создает вторую задачу и повторное уведомление. Если пользователь не найден, найдено несколько пользователей, отсутствует телефон, пользователь неактивен или отсутствует связь со сделкой, каскад не запускается, а ответственному за сделку создается задача с описанием ошибки.

## 7. Автоматизация по стадиям

### Сделка создана

Действия:

- проверить заполнение обязательных полей клиента и ТС;
- перевести сделку на стадию "Запись на дефектовку" для подбора СТОА, мастера и времени.

### Запись на дефектовку

Действия:

- менеджер выбирает СТОА с учетом предпочтений клиента, адреса, графика и доступных окон;
- менеджер выбирает мастера и свободное время;
- при необходимости фиксирует комментарий клиента по предпочтениям;
- создается запись на дефектовку;
- в поле сделки записывается СТОА, а специалист, дата и время сохраняются в связанной онлайн-записи;
- клиенту отправляется подтверждение записи через каскадную рассылку;
- REST-обработчик находит экстранет-пользователя по ID ресурса, создает на него задачу и отправляет ссылку через каскадную рассылку на мобильный телефон из профиля.

Текст задачи мастеру:

```text
Провести дефектовку ТС.

СТОА: [Название, адрес]
Дата и время: [Дата и время]
ТС: [Марка] [Модель]
Госномер: [Госномер]
Клиент: [ФИО]
Телефон: [Телефон]
Описание повреждений: [Описание повреждений]

По итогам дефектовки оставьте комментарий к задаче строго в формате:

Результат: [отказался / думает / согласился на ремонт / не приехал / перенес запись]
Комментарий: [результаты осмотра, выявленные повреждения и рекомендуемые работы]
Ориентировочная стоимость: [сумма или "не определена"]
```

"Требуемый результат" не является отдельным полем сделки. Это инструкция мастеру о составе ответа по итогам дефектовки.

### Дефектовка назначена

Действия:

- при наступлении даты дефектовки ответственному поставить контрольную задачу проверить, получен ли результат.

### Результат дефектовки получен

Ответственный за сделку вручную переносит из комментария задачи:

- значение "Результат" в поле "Результат дефектовки";
- значение "Комментарий" в поле "Комментарий мастера";
- указанную сумму в поле "Ориентировочная стоимость ремонта"; если мастер указал "не определена", поле остается пустым.

Правила перехода:

- "Отказался" -> "Отказ / неуспешно";
- "Не приехал" -> задача менеджеру связаться с клиентом и решить: перенос или отказ;
- "Думает" -> "Клиент думает";
- "Согласился на ремонт" -> "Контроль начала ремонта".

### Клиент думает

Действия:

- ответственному ставится задача связаться с клиентом через заданный срок;
- после ответа клиента сделка переводится в "Контроль начала ремонта" или "Отказ / неуспешно".

### Контроль начала ремонта

Действия:

- ответственному ставится задача проконтролировать начало ремонта;
- если ремонт не начался, фиксируется плановая дата начала;
- факт начала ремонта в Битрикс24 подтверждает ответственный за сделку: заполняет фактическую дату начала и переводит сделку в "Ремонт в работе".

### Ремонт в работе

Действия:

- ответственному ставится задача контролировать плановую дату окончания ремонта;
- при изменении сроков обновляются плановая дата окончания и комментарий.

### Контроль окончания ремонта

Действия:

- факт окончания ремонта в Битрикс24 подтверждает ответственный за сделку: заполняет фактическую дату окончания ремонта;
- указывает в сделке эксперта, который будет осуществлять проверку качества;
- переводит сделку в "Проверка качества".

Порядок выбора эксперта определяется должностной инструкцией ответственного и не входит в данное ТЗ.

### Проверка качества

Действия:

- на эксперта создается задача по проверке качества;
- эксперт проверяет качество ремонта;
- фиксирует результат проверки в комментарии к задаче, закрывает задачу;
- после успешной проверки качества ответственному за сделку автоматически создается задача связаться с клиентом;
- ответственный сообщает клиенту о готовности ТС и рекомендациях по приемке;
- при успешной проверке сделка переводится в "Расчеты";
- при замечаниях создается задача на повторный контроль.

Утвержденный формат комментария эксперта:

```text
Итог проверки: [принято без замечаний / есть замечания / требуется повторная проверка]
Проверенные работы и узлы: [перечень]
Выявленные замечания: [описание или "нет"]
Рекомендации клиенту: [описание или "нет"]
Повторная проверка: [не требуется / требуется до ДД.ММ.ГГГГ]
```

Фото и документы по результатам проверки прикладываются к задаче отдельными файлами.

### Расчеты

Действия:

- ответственный добавляет товар "Комиссия за ремонт";
- вручную вводит сумму комиссии; формула и автоматический расчет комиссии не входят в проект;
- создает счет СТОА на основании сделки в [разделе счетов Битрикс24](https://fs911.bitrix24.ru/crm/type/31/kanban/category/0/);
- после оплаты переводит сделку в "Успешно завершено".

## 8. Уведомления

Клиенту:

- подтверждение записи на дефектовку;
- напоминание о визите;
- ответственное лицо вручную сообщает о готовности ТС после успешной проверки качества.

Мастеру СТОА:

- уведомление о новой записи через каскадную рассылку;
- ссылка на задачу через каскадную рассылку;
- напоминание о необходимости указать результат дефектовки;
- уведомление о запросе информации по началу/окончанию ремонта.

Ответственному Форсайта:

- задача записать клиента на дефектовку: подобрать СТОА, свободного мастера и время;
- задача проверить результат дефектовки;
- задача проконтролировать начало ремонта;
- задача проконтролировать окончание ремонта;
- задача организовать проверку качества;
- задача связаться с клиентом после успешной проверки качества.

Эксперту Форсайта:

- задача по проверке качества ремонта.

## 9. Права доступа

Роли:

- администратор CRM;
- руководитель направления;
- менеджер Форсайта;
- эксперт Форсайта;
- внешний мастер СТОА.

Требования:

- менеджер Форсайта видит и редактирует сделки своей воронки;
- руководитель видит все сделки направления;
- эксперт видит задачи и сделки, где он назначен на проверку качества;
- внешний мастер является экстранет-пользователем;
- задача назначается непосредственно экстранет-пользователю;
- мастер видит только свои задачи и минимальные данные для выполнения дефектовки;
- мастер не получает доступ к воронке CRM и чужим задачам;
- интеграция читает мобильный телефон и пользовательские поля профиля с административными правами и не передает их другим мастерам.

## 10. Этапы внедрения

1. Создать тестовую воронку "Ремонт ТС". 
2. Создать поля карточки сделки. 
3. Создать тип CRM-компании "СТОА" и настроить карточку компании.
4. Завести две тестовые СТОА и по два экстранет-пользователя и ресурса онлайн-записи для каждой.
5. Проверить сценарий записи через "Онлайн-запись" или бронирование ресурсов. 
6. Настроить поля профиля мастера и заполнить ID ресурсов.
7. Реализовать REST-обработчик событий онлайн-записи.
8. Проверить права экстранет-пользователя.
9. Настроить роботов и задачи по стадиям.
10. Протестировать полный путь сделки: создание -> дефектовка -> ремонт -> проверка качества -> расчеты.

## 11. Критерии приемки

Воронка считается настроенной, если:

- менеджер может создать сделку и заполнить обязательные поля;
- менеджер может выбрать СТОА в сделке, а специалиста и время дефектовки — в онлайн-записи;
- занятость мастера видна до записи;
- онлайн-запись со специалистом, датой и временем фиксируется в таймлайне карточки сделки;
- ресурс однозначно сопоставляется с экстранет-пользователем по ID;
- задача назначается найденному экстранет-пользователю;
- мастер получает уведомление и ссылку на задачу по мобильному телефону из профиля;
- перенос, смена мастера и отмена записи актуализируют связанную задачу и уведомления;
- результат дефектовки фиксируется в сделке;
- ответственный получает задачи на контроль начала и окончания ремонта;
- эксперт может зафиксировать результат проверки качества;
- после успешной проверки качества ответственному автоматически создается задача связаться с клиентом;
- на стадии расчетов фиксируется комиссия и статус оплаты.

## 12. Оценка трудозатрат

Предварительная оценка внедрения: 24-34 часа

| Блок работ | Оценка |
| --- |-------:|
| Настройка воронки, стадий и карточки сделки |  1-2 ч |
| Справочник СТОА, поля и связи со сделкой |  1-2 ч |
| Экстранет-пользователи, поля профиля, ресурсы и графики |  3-5 ч |
| REST-обработчик событий, сопоставление и защита от дубликатов |  6-10 ч |
| Роботы, задачи и переходы по стадиям |  2-4 ч |
| Передача телефона и ссылки в каскадную рассылку |  2-3 ч |
| Тестирование основного и ошибочных сценариев |  3-5 ч |
| Исправления после пилота, документация, обучение |  2-4 ч |

Для планирования рекомендуется закладывать 32 часа и резерв 20%, итого около 38 часов.
