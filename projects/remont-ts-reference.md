# Проект "Ремонт ТС": опорные данные

Дата создания: 2026-06-17
Дата актуализации: 2026-08-08

## Назначение проекта

Проект нужен для учета и контроля услуги организации ремонта поврежденного транспортного средства через партнерские СТОА.

Клиент получает рекомендацию СТОА, записывается на дефектовку, далее Форсайт контролирует начало ремонта, окончание ремонта, качество ремонта и расчеты с СТОА за привлеченного клиента.

## Рекомендуемые стадии воронки CRM

1. Сделка создана
2. Запись на дефектовку
3. Дефектовка
4. Дефектовка завершена
5. Клиент думает
6. Контроль начала ремонта
7. Ремонт
8. Проверка качества
9. Проверка качества завершена
10. Расчеты
11. Успешно завершено
12. Отказ / неуспешно

## Справочник СТОА

Для сдачи проекта создаются две тестовые СТОА. В каждой карточке хранятся:

- название;
- адрес;
- телефоны;
- график работы;
- условия комиссии;
- ответственный;
- комментарий.

Для каждой тестовой СТОА создаются по два специалиста онлайн-записи. После сдачи проекта пользователи самостоятельно создают СТОА, специалистов, элементы списка сопоставления и настраивают графики по инструкции.

СТОА хранятся в CRM-компаниях с отдельным типом "СТОА". В сделке используется отдельное пользовательское поле "СТОА" с привязкой к компании. Стандартное поле "Клиент" для этой связи не используется: в нем остается владелец транспортного средства.

При создании специалиста онлайн-записи используется единое правило:

- тип ресурса — точное название компании СТОА, например "Кузя";
- название ресурса — имя мастера, например "Илья Иванов";
- при переименовании компании СТОА одноименный тип ресурсов также переименовывается.

Каждый мастер также создается как экстранет-пользователь Битрикс24. В его профиле обязательны мобильный телефон и активный статус. CRM-контакт мастера не создается, отдельное поле "Мастер СТОА" в сделке не используется.

Авторитетное сопоставление ресурсов, СТОА и экстранет-пользователей хранится в закрытом универсальном списке "Связь ресурсов СТОА". Один элемент списка соответствует одному ресурсу и содержит:

- ID ресурса онлайн-записи — обязательная строка, уникальная среди активных элементов;
- название ресурса — строка для диагностики;
- СТОА — привязка к CRM-компании с типом "СТОА";
- ID экстранет-пользователя — обязательное число;
- пользователь — необязательная привязка к сотруднику, если поле позволяет выбрать экстранет-пользователя;
- активность связи — список "Да/Нет";
- служебный комментарий.

Несколько ресурсов могут ссылаться на одного экстранет-пользователя. Для тестового контура все ресурсы допускается связать с одним пользователем, в профиле которого указан мобильный телефон.

Полный доступ к списку имеют только администраторы и интеграция. Экстранет-пользователям список недоступен.

Проверено под учетной записью экстранет-пользователя: мастер видит собственные дефектовки в личном календаре и утвержденный минимальный набор данных в назначенной задаче, но не имеет доступа к CRM.

При подключении мастера ресурс создается в онлайн-записи, после чего администратор или интеграция добавляет в универсальный список элемент с ID ресурса, компанией СТОА и ID экстранет-пользователя.

Автоматизация подписывается на REST-события онлайн-записи:

- `onBookingAdd` — определяет сделку по внешней связи записи, отсекает повторы и дубли, запускает бизнес-процесс создания задачи и каскадной рассылки;
- `onBookingUpdate` — актуализирует задачу только для записи, указанной в сделке как актуальная, и при смене ресурса переназначает ее новому мастеру;
- `onBookingDelete` — находит сделку по ID актуальной записи, завершает задачу с комментарием об отмене, очищает оба технических ID и уведомляет ответственного;
- связь хранится в технических полях сделки `ID актуальной онлайн-записи` и `ID задачи мастера`.

Задача мастеру создается бизнес-процессом `724`. Все входные параметры обязательные и немножественные: `user_id` — привязка к экстранет-пользователю мастера; `date_from` — дата и время начала дефектовки; `date_to` — дата и время окончания дефектовки и крайний срок задачи. ID созданной задачи сохраняется в поле сделки `UF_CRM_1786012024`. После создания задачи мастер получает через бизнес-процесс каскадной отправки `734` уведомление с автомобилем, датой и временем, СТОА и ссылкой на задачу. Бизнес-процесс `724` также запускает без ожидания процесс `738`, который через час после `date_to` проверяет статус задачи и отправляет мастеру однократное каскадное напоминание, только если задача еще не завершена. Для клиента процесс проверяет телефон основного контакта, запускает шаблон `734` с нейтральным подтверждением записи без обращения по имени и устанавливает статус подтверждения "Отправлено". Если до дефектовки осталось не менее 24 часов, процесс `724` запускает отложенный бизнес-процесс `740` с напоминанием клиенту. Процесс `740` сначала прекращает прежние ожидающие экземпляры для этой сделки, затем в рассчитанное время запускает каскадную отправку; повторное планирование после переноса записи тем самым отменяет устаревшее сообщение. Персональное обращение не используется, поскольку поле "Имя" содержит полное ФИО. Затем бизнес-процесс переводит сделку на стадию "Дефектовка" и создает ответственному задачу проверить результат. После выполнения контрольной задачи сделка переводится на стадию "Дефектовка завершена", где робот маршрутизирует ее по значению поля "Результат дефектовки".

REST-обработчик использует общий входящий вебхук `B24_WEBHOOK_CODE` с правами на `booking`, `lists`, CRM, бизнес-процессы, задачи, уведомления и чтение пользователей. `B24_BOOKING_DELETE_DUPLICATES` по умолчанию выключен и включается после проверки клиентского уведомления при удалении записи.

## Набор полей карточки сделки

### О сделке

| Поле | Тип | Обязательность | Примечание |
| --- | --- | --- | --- |
| Клиент | Контакт CRM | Да | Основной контакт клиента. |
| Сумма комиссии | Деньги | Да на стадии "Расчеты" | Вводится ответственным вручную. Правила расчета комиссии не входят в проект. |
| Статус оплаты от СТОА | Список | Да на стадии "Расчеты" | Не выставлено, выставлено, оплачено, просрочено. |

Название сделки автоматически формируется при создании и обновляется при изменении сделки по шаблону `[Имя контакта] [Марка, модель а/м]`.

### Транспортное средство

| Поле | Тип | Обязательность | Примечание |
| --- | --- | --- | --- |
| Марка, модель а/м | Строка | Да | Используется существующее поле из другой воронки, новое поле не создается. |
| Г/н | Строка | Да | Желательно единый формат ввода. |
| VIN | Строка | Нет | Нужен, если СТОА или эксперты используют VIN в работе. |
| Описание повреждений | Многострочный текст | Да | Краткое описание со слов клиента/менеджера. |
| Фото повреждений | Файл | Нет | Если процесс будет требовать первичной фиксации. |

### СТОА и запись

| Поле | Тип                         | Обязательность | Примечание |
| --- |-----------------------------| --- | --- |
| СТОА | Привязка к компании CRM     | Да со стадии "Запись на дефектовку" | Выбирается компания с типом "СТОА"; стандартное поле "Клиент" не используется. |
| Статус подтверждения записи | Список                      | Нет | Не отправлено, отправлено, подтверждено, перенесено, отменено. |
| ID актуальной онлайн-записи | Строка | Техническое | Код `UF_CRM_1786012014`. Заполняется и очищается только интеграцией; используется для идемпотентности и обработки удаления. |
| ID задачи мастера | Строка | Техническое | Код `UF_CRM_1786012024`. Заполняется бизнес-процессом после создания задачи; перед обновлением проверяется существование задачи через REST. |

Отдельные пользовательские поля "Мастер СТОА", "Адрес СТОА" и "Дата и время дефектовки" в сделке не создаются:

- мастер и дата/время хранятся и отображаются в связанной онлайн-записи;
- адрес хранится в связанной карточке СТОА;
- дублирующие поля следует добавлять только при подтвержденной необходимости для роботов, шаблонов сообщений, фильтров, экспорта или BI-отчетов, если нужные данные нельзя получить из онлайн-записи или связанной СТОА.

Ресурс и границы слота берутся из онлайн-записи, СТОА и ID пользователя — из универсального списка, адрес — из карточки компании. Крайний срок задачи мастеру равен времени окончания слота дефектовки.

### Дефектовка

| Поле | Тип | Обязательность | Примечание |
| --- | --- | --- | --- |
| Результат дефектовки | Список | Да после дефектовки | Отказался, думает, согласился на ремонт, не приехал, перенес запись. |
| Комментарий мастера | Многострочный текст | Да после дефектовки | Ответственный вручную переносит содержательный комментарий из задачи. Если замечаний нет, указывается "Без дополнительных замечаний". |
| Ориентировочная стоимость ремонта | Деньги | Нет | Если СТОА готова передавать оценку. |

Мастер оставляет комментарий к задаче в формате:

```text
Результат: [отказался / думает / согласился на ремонт / не приехал / перенес запись]
Комментарий: [результаты осмотра, выявленные повреждения и рекомендуемые работы]
Ориентировочная стоимость: [сумма или "не определена"]
```

Ответственный за сделку вручную переносит данные из комментария задачи в соответствующие поля сделки.

### Ремонт

| Поле | Тип | Обязательность | Примечание |
| --- | --- | --- | --- |
| Плановая дата начала ремонта | Дата | Нет | Заполняется после согласия клиента. |
| Фактическая дата начала ремонта | Дата | Нет | Заполняется ответственным за сделку при подтверждении начала ремонта. |
| Плановая дата окончания ремонта | Дата | Нет | Используется для контроля. |
| Фактическая дата окончания ремонта | Дата | Нет | Заполняется ответственным за сделку при подтверждении окончания ремонта. |
| Статус ремонта | Список | Нет | Не начат, в работе, приостановлен, завершен. |

На стадии "Контроль начала ремонта" робот устанавливает статус ремонта "Не начат" и создает ответственному задачу "[ФИО клиента] [Марка, модель а/м]: Проконтролировать начало ремонта". Задача создается без крайнего срока, так как плановая дата начала ремонта может быть еще неизвестна.

```text
1. Связаться с СТОА, собрать информацию.
2. Заполнить плановые даты начала и окончания ремонта.
3. Проконтролировать начало ремонта, заполнить фактическую дату начала ремонта.
4. Перевести сделку на стадию "Ремонт".
```

После выполнения задачи робот переводит сделку в "Ремонт". Ответственный завершает задачу только после подтверждения начала ремонта и заполнения фактической даты.

При входе на стадию "Ремонт" робот устанавливает статус ремонта "В работе" и создает ответственному связанную со сделкой задачу:

- название: `[ФИО клиента] [Марка, модель а/м]: Проконтролировать окончание ремонта`;
- крайний срок: значение поля "Плановая дата окончания ремонта";
- чек-лист:
  1. Проконтролировать ремонт, заполнить фактическую дату окончания ремонта.
  2. Указать эксперта для контроля качества.
  3. Перевести сделку на стадию "Проверка качества".

Ответственный указывает эксперта в карточке сделки до завершения задачи. После выполнения задачи робот переводит сделку в "Проверка качества". Первым роботом этой стадии статус ремонта устанавливается в "Завершен".

### Проверка качества

| Поле | Тип | Обязательность | Примечание |
| --- | --- | --- | --- |
| Эксперт | Пользователь | Нет | Ответственный за проверку качества. |
| Дата проверки качества | Дата/время | Нет | |
| Результат проверки качества | Список | Да на стадии "Проверка качества" | Принято без замечаний, есть замечания, требуется повторная проверка. |
| Комментарий эксперта | Многострочный текст | Нет | Рекомендации клиенту по приемке ТС. |

Утвержденный формат комментария эксперта:

```text
Итог проверки: [принято без замечаний / есть замечания / требуется повторная проверка]
Проверенные работы и узлы: [перечень]
Выявленные замечания: [описание или "нет"]
Рекомендации клиенту: [описание или "нет"]
Повторная проверка: [не требуется / требуется до ДД.ММ.ГГГГ]
```

Фото и документы по результатам проверки прикладываются к задаче отдельными файлами.

При входе на стадию "Проверка качества" робот устанавливает статус ремонта "Завершен" и проверяет поле "Эксперт". Если поле пустое, ответственному создается задание автоматизации на выбор эксперта, а выбранный пользователь сохраняется в сделку. После этого пользователю из поля "Эксперт" создается связанная со сделкой задача:

- название: `[ФИО клиента] [Марка, модель а/м]: Провести проверку качества ремонта`;
- крайний срок: значение поля "Дата проверки качества";
- описание: проверить выполненные работы и отремонтированные узлы, зафиксировать замечания и результат проверки качества по утвержденному формату, приложить фотографии и документы при наличии.

О назначении задачи эксперт уведомляется штатными средствами Битрикс24. Отдельная каскадная рассылка или другая внешняя интеграция для эксперта не используется.

Утвержденный формат комментария эксперта добавлен непосредственно в описание задачи.

После завершения задачи эксперта ответственному за сделку создается связанная со сделкой задача `[ФИО клиента] [Марка, модель а/м]: Зафиксировать результат проверки качества` с чек-листом:

```text
1. Проверить результат проверки качества.
2. Заполнить поле "Дата проверки качества".
3. Заполнить поле "Результат проверки качества".
4. Заполнить поле "Комментарий эксперта".
```

После выполнения задачи сделка переводится в "Проверка качества завершена". На этой контрольной стадии результат "Есть замечания" переводит сделку в "Ремонт", "Требуется повторная проверка" — в "Проверка качества". При пустом или неизвестном результате сделка остается на стадии для ручной обработки.

При результате "Принято без замечаний" ответственному создается связанная со сделкой задача `[ФИО клиента] [Марка, модель а/м]: Сообщить о готовности ТС` со сроком один день. Ответственный сообщает клиенту о завершении ремонта и успешной проверке качества, передает рекомендации эксперта, согласовывает получение автомобиля и фиксирует результат разговора в комментарии. После выполнения задачи робот переводит сделку в "Расчеты".

Счет СТОА создается на основании сделки как отдельный документ в разделе ["Счета"](https://fs911.bitrix24.ru/crm/type/31/kanban/category/0/) и на первую вкладку сделки не выводится.

## Задача по подбору СТОА

При переходе сделки на стадию "Запись на дефектовку" ответственному за сделку создается задача "[ФИО клиента] [Марка, модель а/м]: Подобрать СТОА" со сроком один рабочий день. Задача завершается после создания онлайн-записи; на стадию "Дефектовка" сделку автоматически переводит бизнес-процесс `724` после создания задачи мастеру.

```text
Подберите СТОА, мастера и время дефектовки.

Клиент: [ФИО клиента]
Телефон: [Телефон]
ТС: [Марка, модель а/м]
Г/н: [Г/н]
Описание повреждений: [Описание повреждений]
Комментарий: [Комментарий]
```

Чек-лист задачи:

```text
1. Уточнить у клиента подходящие дату, время и расположение СТОА.
2. Выбрать СТОА в карточке сделки.
3. Проверить свободные окна мастеров в онлайн-записи.
4. Создать онлайн-запись на выбранного мастера.
5. Завершить задачу после создания онлайн-записи; смена стадии выполняется автоматически.
```

## Контроль результата дефектовки

Бизнес-процесс `724` создает ответственному задачу "[ФИО клиента] [Марка, модель а/м]: Проверить результат дефектовки" с датой и временем дефектовки и чек-листом:

```text
1. Проверить ответ мастера и заполнить поле "Результат дефектовки".
2. Заполнить поле "Комментарий мастера".
3. Указать ориентировочную стоимость ремонта, если она определена.
```

После заполнения полей и выполнения задачи бизнес-процесс переводит сделку на стадию "Дефектовка завершена". На стадии настроены три условных робота: "Отказался" — перевод в "Отказ / неуспешно", "Думает" — в "Клиент думает", "Согласился на ремонт" — в "Контроль начала ремонта". Результаты "Не приехал" и "Перенес запись" автоматически не обрабатываются: сделка остается на стадии, а дальнейшее действие определяет ответственный.

Стадия "Дефектовка завершена" выделена красным цветом и используется как контрольная очередь. Ее следует держать пустой; наличие сделок показывает руководителю, что есть клиенты с необработанным исходом дефектовки.

## Повторный контакт с клиентом

На стадии "Клиент думает" бизнес-процесс создает ответственному связанную со сделкой задачу "[ФИО клиента] [Марка, модель а/м]: Повторно связаться с клиентом" с крайним сроком через три календарных дня. Ответственный связывается с клиентом до получения окончательного решения и меняет поле "Результат дефектовки" на "Согласился на ремонт" или "Отказался".

После выполнения задачи бизнес-процесс переводит согласившегося клиента в "Контроль начала ремонта", отказавшегося — в "Отказ / неуспешно". Любое другое значение возвращает сделку в "Дефектовка завершена", после чего переход в "Клиент думает" запускает новый цикл повторного контакта.

```text
Требуется связаться с клиентом, чтобы получить окончательный ответ.
Ответ зафиксировать в поле "Результат дефектовки": Согласился на ремонт или Отказался.
```

## Подтвержденные исходные условия

- Битрикс24: облачная версия, тариф "Профессиональный".
- Функция "Онлайн-запись" доступна в портале.
- Мастеров СТОА можно завести как ресурсы бронирования или специалистов.
- Менеджер Форсайта может вручную создавать онлайн-запись из CRM-сделки.
- Запись онлайн-записи можно хранить в карточке сделки.
- Штатную автоматизацию можно запускать от создания онлайн-записи.
- REST API предоставляет события создания, изменения и удаления онлайн-записи.
- У каждого мастера должен быть отдельный график приема.
- Каждый мастер является экстранет-пользователем и может работать со своей задачей без доступа к лишней CRM.
- Клиент получает через каскадную рассылку подтверждение сразу после создания записи, напоминание за 24 часа до визита, а также сообщения сразу после переноса или отмены. Для записи, созданной менее чем за 24 часа до визита, отдельное напоминание не отправляется. Напоминание планируется процессом `740`, который при повторном запуске для сделки отменяет прежнее ожидающее напоминание. Утвержденные тексты хранятся в разделе 8 ТЗ.
- После завершения ремонта и успешной проверки качества ответственному за сделку автоматически создается задача связаться с клиентом и сообщить о готовности ТС.
- Телефон мастера хранится в профиле экстранет-пользователя, а связь ресурса, СТОА и пользователя — в закрытом универсальном списке.
- Мастер получает уведомление о назначении дефектовки и ссылку на назначенную ему задачу через каскадную рассылку.
- Каскадная рассылка уже настроена в системе: Макс -> WhatsApp -> Telegram -> SMS.
- Отдельный резервный канал уведомлений мастера не требуется.
